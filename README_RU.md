# auth-hub

Документ описывает рефакторенную, разложенную по слоям версию проекта (`Login/project`), а не более раннюю плоскую версию, лежащую рядом в родительской папке.

Сервис аутентификации в реальном времени на Go: bcrypt-хэширование паролей, сессии на cookie, и WebSocket-хаб, транслирующий подключённым клиентам живую активность входов и счётчик пользователей онлайн.

## Обзор

`auth-hub` обрабатывает регистрацию и вход через серверно-рендеренные HTML-формы, хранит учётные данные в PostgreSQL с bcrypt-хэшированными паролями и отслеживает сессии через cookie, сопоставленный с ID пользователя.

Поверх этой базы добавлен WebSocket-хаб: каждая вкладка браузера, подключившаяся к `/ws`, отслеживается и по соединению, и по cookie сессии, а хаб транслирует всем подключённым клиентам живой лог активности (события входа, ошибки, произвольные записи лога) и счётчик пользователей онлайн. Об успешном входе браузер узнаёт именно через этот WebSocket-канал, а не только через HTTP-ответ.

Это рефакторинг более ранней однопакетной версии того же приложения (лежит рядом, в родительской папке `Login/`): та же логика авторизации/сессий/хаба, но разложенная на отдельные пакеты `auth`, `database`, `handlers`, `models`, `socket`, с `context.Context`, протянутым от входящего запроса до слоя БД и WebSocket.

## Возможности

- Регистрация и вход через серверно-рендеренные HTML-формы (`html/template`)
- Пароли хэшируются через bcrypt (`golang.org/x/crypto/bcrypt`) — в открытом виде не хранятся никогда
- Управление сессиями на cookie (`session_id`, сопоставлен с ID пользователя)
- Auth-middleware защищает `/logout`, `/dashbord`, `/profile`, `/settings`, `/data`, перенаправляя неаутентифицированные запросы на `/login`
- WebSocket-хаб (`/ws`), который:
  - отслеживает несколько одновременных соединений на одну сессию пользователя (со счётчиком по cookie)
  - транслирует ограниченный (100 записей) кольцевой лог активности, который проигрывается заново подключившимся клиентам
  - показывает живой счётчик пользователей онлайн
  - поддерживает ping/pong keepalive-сообщения
  - отправляет события редиректа и ошибки в конкретную сессию пользователя в ответ на попытку входа
- `context.Context` запроса протянут от HTTP-хендлера в вызовы БД и в жизненный цикл WebSocket-соединения (отменяется при отключении)
- Разделение по пакетам: `auth`, `database`, `handlers`, `models`, `socket`

## Архитектура

```text
Браузер
  |
  |--(HTML-формы: /register, /login)--> Handler --> Database (PostgreSQL)
  |                                        |
  |                                        +--> auth (bcrypt, cookie-сессия)
  |
  +--(WebSocket: /ws)--------------------> Hub
                                              |
                                              +-- clients map (по соединению)
                                              +-- sessionsocket map (cookie -> соединение)
                                              +-- LogStorage (кольцевой буфер, рассылка всем клиентам)
```

## Модель конкурентности

- **Горутина на соединение**: каждое принятое WebSocket-соединение работает в своей горутине-хендлере (`hub.WebSocket`, `socket/hub.go`), блокируясь в цикле чтения на всё время жизни соединения.
- **Контекст на соединение**: `context.WithCancel(r.Context())` создаётся на каждое соединение и отменяется через `defer cancel()` при выходе из цикла чтения — используется, чтобы остановить `SendLogsHistory`, если клиент отключился до завершения отправки истории.
- **Синхронизация хаба**: единый `sync.Mutex` защищает `clients`, `clientscookie`, `sessionsocket`, `onlineUsers` (`socket/socket.go`). Методы рассылки (`SendNotification`, `SendLog`, `SendClient`) копируют список клиентов под блокировкой, а пишут в сокеты уже после её снятия — мьютекс не удерживается во время сетевого I/O.
- **Лог активности**: `LogStorage` использует отдельный `sync.RWMutex` (`socket/comandsoket.go`) — чтение (`GetAll`) берёт read-lock, запись (`Add`) — write-lock, буфер обрезается до фиксированного максимума (100 записей) при каждом добавлении.
- **Хранилище сессий**: пакетная `map[string]int`, защищённая `sync.Mutex` (`auth/cookie.go`), сопоставляет значение cookie сессии с ID пользователя — только в памяти, не персистится, не разделяется между инстансами.
- `sync.WaitGroup` для скоординированного завершения не используется; каждое соединение само освобождает ресурсы через `defer`.

## Данные / хранение

- **PostgreSQL** через `github.com/jackc/pgx/v5`, без ORM. Единственное соединение `*pgx.Conn` (не пул) создаётся при старте и используется всеми запросами совместно.
- Схема (по запросам в `database/db.go`): таблица `user_app` как минимум с колонками `id`, `username`, `password_hash`. Файлов миграций нет — таблица должна существовать заранее.
- Методы запросов: `CheckUser` (проверка существования), `RegisterUser` (вставка), `GetDataUser` / `GetUserById` (поиск по username / ID) — все параметризованы (`$1`, `$2`, ...).
- Строка подключения к PostgreSQL читается из переменной окружения `DATABASE_URL`, а если она не задана — используется дефолт для локальной разработки (`host=localhost port=5432 user=postgres password=postgres dbname=postgres sslmode=disable`).

## Отказоустойчивость / обработка ошибок

- `context.Context` входящего HTTP-запроса протянут в вызовы БД (`CheckUser`, `GetDataUser`, `GetUserById`) и в жизненный цикл WebSocket-соединения — отмена распространяется дальше, а не игнорируется молча.
- Цикл чтения WebSocket отличает ожидаемое закрытие (`websocket.IsCloseError` для going-away / normal-closure) от прочих ошибок чтения — однако при *неожиданной* ошибке код сейчас не делает `continue`/`return` перед попыткой обработать сообщение, что на этом пути может привести к обработке устаревших данных (см. *Current limitations*).
- Отсутствует: повторные попытки, логика переподключения, circuit breaking. Это обычный возврат ошибок, а не fault tolerance.

## Безопасность

- Пароли хэшируются через `bcrypt.GenerateFromPassword` / проверяются через `bcrypt.CompareHashAndPassword` (стандартная стоимость) — в открытом виде пароли не хранятся никогда.
- Значения сессии и cookie генерируются через `crypto/rand`, не `math/rand`.
- `auth.AuthMiddleware` проверяет наличие валидного cookie `session_id`, сопоставленного с известной сессией, перед допуском к защищённым маршрутам.
- Все SQL-запросы параметризованы.
- Отсутствует: CSRF-защита форм логина/регистрации, ограничение origin при апгрейде WebSocket (`CheckOrigin` всегда возвращает `true`), настройка HTTPS/TLS, rate limiting на попытки входа, серверная очистка просроченных сессий (`Expires` у cookie — это только клиентская сторона).

## Структура проекта

```text

auth/         хэширование паролей, cookie-сессии, auth-middleware

```

## Запуск локально

Требуется доступный инстанс PostgreSQL с уже созданной таблицей `user_app` (миграций нет):

```bash
go mod download
export DATABASE_URL="host=localhost port=5432 user=postgres password=postgres dbname=postgres sslmode=disable"
go run .
```

Если `DATABASE_URL` не задана, `main.go` использует тот же дефолт для локальной разработки. Сервер слушает `:9090`.

## Инженерные решения

- **WebSocket-хаб, ключом для которого служит и соединение, и cookie сессии, со счётчиком по cookie** — позволяет одному залогиненному пользователю иметь несколько вкладок/соединений одновременно, при этом счётчик "пользователей онлайн" отражает уникальных пользователей, а не соединения.
- **Успешный вход отправляется через уже открытое WebSocket-соединение** (`SocketRedirect`), а не обычным HTTP-редиректом — поток логина переиспользует тот же realtime-канал, что и остальная лента активности, вместо отдельного механизма.
- **Ограниченный кольцевой буфер лога (максимум 100 записей)** вместо неограниченного лога — держит потребление памяти постоянным независимо от времени жизни процесса, ценой хранения только недавней истории.
- **`context.Context` протянут от HTTP-запроса и в слой БД, и в жизненный цикл WebSocket-соединения** — отключение клиента или отмена запроса видны дальше по стеку вызовов, а не игнорируются молча.
- **Разделение на пакеты `auth` / `database` / `handlers` / `models` / `socket`**, рефакторинг из однопакетной предыдущей версии — разделяет логику сессий/паролей, персистентность, HTTP-оркестрацию и realtime-слой на независимо читаемые части.

## Текущие ограничения

- Хранилище сессий в памяти, в рамках одного процесса (`map[string]int` в `auth`) — сессии теряются при перезапуске и не могут быть общими между несколькими инстансами; записи никогда не очищаются по истечении срока на сервере.
- Гонка данных: в `auth.SetCookieuser` ветка с уже существующим cookie пишет в общую map `session` без захвата пакетного мьютекса, в отличие от всех остальных мест записи в эту map.
- Нет CSRF-защиты форм логина/регистрации; `CheckOrigin` у WebSocket принимает любой origin.
- Маршрут `/loader` ссылается на `html/loader.html`, которого нет в репозитории — этот маршрут сейчас не работает.
- Нет автоматических тестов, нет миграций БД (схема должна существовать заранее), нет graceful shutdown.
- POST-хендлер логина одновременно вызывает `ParseForm()` и JSON-декодирует тело запроса — не согласуется с хендлером регистрации, который использует только form-значения.

## Возможные следующие шаги

- Добавить CSRF-защиту и ограничить `CheckOrigin` у WebSocket известными origin'ами.
- Заменить хранилище сессий в памяти на хранилище с поддержкой истечения срока и нескольких инстансов (например, сессии на Redis).
- Добавить тесты для `auth` (хэширование паролей, обработка сессий) и логики отслеживания клиентов в WebSocket-хабе.
